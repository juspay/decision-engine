## What It Shows

Payment Audit is the operator-facing timeline view for a single payment or request.

Use it when you want to answer questions like:

- which gateway was decided for this payment
- which rule was evaluated, and which priority rule was hit
- whether a score update succeeded or failed
- what structured event payload was captured at each step

Every payment is one entry. Its trail holds every audit event recorded for that payment,
whatever produced it - the rule evaluation, the gateway decision, the later score update, and
any errors. A payment routed through `/routing/hybrid` reads as `routing_hybrid_decision`
(Hybrid Routing - one event carrying the whole hybrid request and response, the connector
scores and the selection reason) → `update_gateway_score_update` (Update Gateway).

The page is designed for exact lookups first and broad operator filtering second.

## Search Inputs

The page supports these filters:

- `payment_id`
- `request_id`
- `routing_kind`
- `gateway`
- `route`
- `outcome` — the payment's outcome (the page's outcome dropdown), one or several, see below
- `status` — an event's exact status (e.g. `FAILURE`); for what happened to the payment, use
  `outcome`
- `flow_type`
- payment attributes (under **More filters**): `payment_method`, `payment_method_type`,
  `card_network`, `auth_type`, `currency`, `min_amount`, `max_amount`
- time window: `15m`, `1h`, `12h`, `1d`, `1w`

### Outcome

A payment's outcome comes from the statuses reported for it on `/update-gateway-score`:

| Outcome | Meaning |
| --- | --- |
| `success` | An attempt succeeded (e.g. `CHARGED`), including after failed retries. |
| `failure` | An attempt failed terminally (e.g. `AUTHORIZATION_FAILED`) and none succeeded. |
| `pending` | No terminal status reported yet (only routing events, or e.g. `PENDING_VBV`). |

A routing call's own `success` status is the API call's result, not the payment's, and never
counts. The success / failure totals above the results use the same outcome. Pick several outcomes
(`outcome=failure,pending`) to see payments with any of them.

### Payment attributes

Payment attributes come from the payment's routing decision. On `/routing/hybrid` they are the
rule parameters Hyperswitch sends, so they follow Hyperswitch's meaning: `payment_method` is
`card`, `wallet`, `upi`… and `payment_method_type` is `credit`, `debit`, `google_pay`…. On
`/decide-gateway` they are the decider request's `paymentMethodType` (e.g. `CARD`) and
`paymentMethod` (e.g. `VISA`). Each takes several values (comma-separated in the API, e.g.
`currency=USD,EUR`) and matches a payment with any of them. Values match case-insensitively, and
the amount bounds are inclusive.

The dropdowns list what the merchant's own payments carried in the selected window, read from
`GET /analytics/payment-audit/filter-options` (same `range` / `start_ms` / `end_ms`), so each
merchant sees its own gateways, methods, networks and currencies rather than a fixed list. Gateway,
route, outcome and the attributes all take several values.

They select whole payments: a matching payment keeps all its events, including the score
updates that carry no attributes, so its outcome still reads correctly. These filters read the
raw event table rather than the pre-aggregated summaries, so keep the time window narrow on busy
merchants.

### Page size and query cost

Results page at 10, 20 (default), 50 or 100 payments; the API accepts `page_size` up to 100. A
search runs four ClickHouse reads (count, page keys, page rows, A/B assignments), the selected
payment three (summary, timeline, A/B assignments), and the dropdown values one per time window,
cached for a minute. Multi-select dropdowns search once when their list closes, not on every
tick. Every read is merchant-scoped and goes through the analytics query guard (a few concurrent
reads per pod, a time limit and memory-bounded settings).

Use an exact `payment_id` when you have it. If you only have a request trace, use `request_id`.
Payment Audit is always merchant-scoped by the authenticated JWT or API key. The route does not
accept `scope` or `merchant_id` query params.

## Timeline Stages

The timeline is built from analytics events captured by the live request flows.

Current stages include:

- `gateway_decided`
- `hybrid_routed`
- `rule_applied`
- `score_updated`
- `preview_evaluated`
- `request_read_failed`
- `validation_failed`
- `request_parse_failed`
- `score_update_failed`

The raw flow type remains visible as well, for example `decide_gateway_decision`,
`decide_gateway_rule_hit`, `update_gateway_score_update`, `routing_evaluate_advanced`, or
`routing_hybrid_decision`.

## A/B Experiments

In the search results, a payment routed under an A/B experiment is tagged **A/B · control** or
**A/B · variant**; untagged payments were not in one. Opening a payment shows the same badge next
to its status, with the endpoint that split it (`hybrid routing`, `decide gateway` or
`rule evaluate`) and a link to the experiment, or **Not in an A/B experiment** — including
payments Hyperswitch routed itself, such as straight-through, which never reach the Decision
Engine.

Each search result carries its assignments in `experiments`. They come from the experiment's own
routing events, which stay out of the timeline so they don't change its event counts.

## Data Sources

Payment Audit reads from the same ClickHouse analytics store used by the analytics surface.

The read path is split intentionally:

- exact `payment_id` / `request_id` lookups read the raw `analytics_domain_events` timeline
- broad search results read the pre-aggregated `analytics_payment_audit_lookup_summaries`,
  merging its per-kind rows (`preview`, `hybrid`, `dynamic`) into one row per payment.

Both views correlate events through the write-time `lookup_key`, which prefers `payment_id` and
falls back to `request_id`.

Relevant fields include:

- `merchant_id`
- `payment_id`
- `request_id`
- `event_stage`
- `route`
- `gateway`
- `routing_approach`
- `rule_name`
- `status`
- `error_code`
- `error_message`
- `details`

The `details` field is shown as structured JSON when available.
