# Merchants and Profiles

A **merchant** is your account in Decision Engine. A **profile** is a part of that merchant with its own routing rules: one per region, brand or business line.

```
Merchant  acme            ← your account: members, API keys
├── Profile  pro_india    ← its own rules, scores and analytics
└── Profile  pro_us       ← its own rules, scores and analytics
```

The merchant holds everything about **who** has access. Each profile holds **how** its payments are routed.

| | Merchant | Profile |
| --- | --- | --- |
| Routing rules, scores, analytics, settings | Its own | Its own |
| Members | Held here | Same as its merchant |
| API keys | Held here | Same as its merchant |

A merchant keeps its own routing rules too, so an existing merchant works exactly as before once you add profiles to it.

## One API key for every profile

An API key created on a merchant works for that merchant and **every one of its profiles**, including profiles added later. Name the profile in each routing call:

```bash
curl "$BASE_URL/decide" \
  --header "x-api-key: $ACME_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "merchant_id": "acme",
    "profile_id": "pro_india",
    "payment_id": "pay_1",
    ...
  }'
```

| Request | Rules used |
| --- | --- |
| `merchant_id: acme` | Acme's own, as before |
| `merchant_id: acme`, `profile_id: pro_india` | Acme India's |
| `merchant_id: pro_india` | Acme India's (the profile id alone also works) |
| `merchant_id: acme`, `profile_id` of another merchant's profile | `400` |
| `merchant_id` of another merchant | `403` |

`profile_id` is accepted by `/decide`, `/update-gateway-score`, and `/decide-gateway` (as `profileId`, in that endpoint's camelCase). Configuration endpoints take the profile id wherever they take a `merchant_id`.

A profile has no keys of its own. Listing, creating or revoking keys from a profile acts on its merchant's keys, so the dashboard's API Keys page shows the same keys on the merchant and on each profile. Revoking a merchant's key revokes it for every profile.

## Members

People are invited to the **merchant**. A member reaches the merchant and all of its profiles with the same role, and a profile added later is reachable at once. Inviting from inside a profile invites to its merchant. There is no per-profile membership.

| Action | Admin | Member |
| --- | --- | --- |
| View and edit routing on the merchant and its profiles | ✅ | ✅ |
| Add a profile | ✅ | — |
| Create or revoke API keys | ✅ | — |
| Invite people | ✅ | — |

## Adding a profile

In the dashboard, open the account switcher and choose **Add profile**. It appears for admins only. Through the API:

```bash
curl "$BASE_URL/onboarding/merchant" \
  --header "Authorization: Bearer $TOKEN" \
  --header "Content-Type: application/json" \
  --data '{ "merchant_name": "Acme India", "parent_merchant_id": "acme" }'
```

Operators can do the same with the admin secret through [`/merchant-account/create`](/api-refs/merchant-account-create), passing `parent_merchant_id`.

Profiles are one level deep: a profile can't have profiles of its own.

## Hyperswitch accounts

Accounts synced from Hyperswitch keep the organization → merchant → profile tree Hyperswitch manages. Their profiles, members and access are managed in Hyperswitch, and Hyperswitch calls Decision Engine with the admin secret. So in Decision Engine you can't add profiles to them, and Hyperswitch sessions can't create or revoke API keys.
