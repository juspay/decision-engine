# Update Gateway Score

## Use case

Records the observed transaction outcome for a previously selected gateway so auth-rate analytics can learn from real payment results.

## Authentication

Protected. Send either `Authorization: Bearer <jwt_token>` or `x-api-key: <api_key>`. In sandbox, also send `x-feature: decision-engine`.

For local development, start with:

```bash
export BASE_URL=http://localhost:8080
export AUTH_HEADER="Authorization: Bearer <jwt_token>"
# Sandbox only:
# export BASE_URL=https://sandbox.hyperswitch.io
# export FEATURE_HEADER="x-feature: decision-engine"
```

## Request

- Method and path: `POST /update-gateway-score`
- Parameters: none.
- Body: JSON body should include merchant/payment identity, selected gateway, status, and latency/outcome details expected by the score updater.

## Example

### Update gateway score

```bash
curl --location "$BASE_URL/update-gateway-score" \
  --header "$AUTH_HEADER" \
  --header "Content-Type: application/json" \
  --data '{
  "merchantId": "merchant_demo",
  "paymentId": "pay_sr_001",
  "gateway": "stripe",
  "status": "CHARGED",
  "gatewayReferenceId": "stripe_ref_001",
  "enforceDynamicRoutingFailure": false,
  "txnLatency": { "gatewayLatency": 120.5 }
}'
```

### Name the connector as `/decide` returned it

Send `attemptedConnector` instead of `gateway`: copy the connector the payment was attempted on
from the `connectors` of its `/decide` response, unchanged.

```bash
curl --location "$BASE_URL/update-gateway-score" \
  --header "$AUTH_HEADER" \
  --header "Content-Type: application/json" \
  --data '{
  "merchantId": "merchant_demo",
  "paymentId": "pay_sr_001",
  "attemptedConnector": { "connector": "stripe", "merchant_connector_id": "mca_stripe" },
  "status": "AUTHORIZATION_FAILED"
}'
```

An update that sends `attemptedConnector` is checked against the payment's latest stored `/decide`
decision before it is accepted:

| Case | Answer |
|---|---|
| A connector the decision offered, first or a later retry | `200`, scored under `stripe:mca_stripe` |
| Another account of the connector, a bare name (`merchant_connector_id` null), or a connector it did not offer | `422` `CONNECTOR_NOT_OFFERED`; the message lists the connectors it offered |
| No decision is stored for the payment: routed by its rule with rule-routed scoring off, or past its scoring-context TTL (a redelivered webhook) | `200`, nothing to score, as a `gateway` update |
| `gateway` sent too and names another connector | `400` `CONNECTOR_MISMATCH` |
| An unknown key inside `attemptedConnector` | `400` |

A payment decided again checks against its latest decision. A decision stored without a connector
list (the decider found no connector, so the request's fallback answered), or one that cannot be read,
is not checked. An update that sends only `gateway` is not checked
at all and behaves as before.

`attemptedConnector` is the connector account `/decide` returned. It is unrelated to
`gatewayReferenceId`, which only splits scores further for merchants with gateway-reference-id
scoring enabled.

`status` must be a transaction status value - `CHARGED`, `AUTHORIZATION_FAILED`,
`AUTHENTICATION_FAILED`, `JUSPAY_DECLINED`, `FAILURE`, and so on. Lowercase values such as
`success` are rejected with a 400.

Payment attributes (amount, currency, payment method, auth type) are **not** part of this
payload - the engine already has them from the `/decide-gateway` call for this `paymentId`.
Any unrecognised field is silently ignored, so a misspelled key fails quietly rather than
erroring. Note in particular that latency goes in `txnLatency.gatewayLatency`, not `latency`.

## Response

```json
{
  "message": "Gateway score updated successfully",
  "merchant_id": "merchant_demo",
  "gateway": "stripe",
  "payment_id": "pay_sr_001"
}
```

When `errorInfo` is supplied in the request and matches a gateway status map rule, the response
also carries a `gsm_info` object describing the lookup result. The rule is matched on the connector
name, so `gateway` may carry its merchant connector id (`checkout:mca_cko` matches rules for `checkout`).
The connector comes from `gateway`, so `errorInfo` does not repeat it; a `connector` field there is ignored.

```json
"errorInfo": {
  "flow": "Payment",
  "subFlow": "Authorize",
  "errorCode": "20068",
  "errorMessage": "Response received too late",
  "issuerErrorCode": null,
  "cardNetwork": null
}
```

When `gsm_info.decision` is `retry`, `gsm_info.retryConnectors` lists the connectors to retry the
payment on, best current success rate first: those `/decide` found eligible for this payment, without
the one that just failed or any already reported for it. Entries are `connector:merchant_connector_id`,
the identifiers `/decide` returns; report the retry attempt with that exact `gateway` and
`isSmartRetry: true`. It is `[]` when every eligible connector has been tried, and `null` for `do_default`.

```json
{
  "message": "Gateway score updated successfully",
  "merchant_id": "merchant_demo",
  "gateway": "checkout:mca_cko",
  "payment_id": "pay_sr_001",
  "gsm_info": {
    "decision": "retry",
    "stepUpPossible": false,
    "clearPanPossible": false,
    "alternateNetworkPossible": false,
    "retryConnectors": ["worldpay:mca_wp", "adyen:mca_ad"],
    "unifiedCode": "UE_3000",
    "unifiedMessage": "Technical issue with PSP",
    "errorCategory": null,
    "standardisedCode": null,
    "description": null,
    "userGuidanceMessage": null
  }
}
```

## Notes

- Do not call this after `NTW_BASED_ROUTING` just to record the selected debit network; debit audit comes from `/decide-gateway` analytics.
- Call it after payment authorization completes, not before.
