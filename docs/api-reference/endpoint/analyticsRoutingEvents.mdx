# Routing Events

## Use case

Returns a historical feed of routing-relevant state changes: SR leader changes, gateways entering or exiting the multi-objective auth band, and autopilot calibration runs. Powers the dashboard's routing timeline and the simulation UI's "Autopilot Actions" panel.

## Authentication

Protected. Send either `Authorization: Bearer <jwt_token>` or `x-api-key: <api_key>`. In sandbox, also send `x-feature: decision-engine`.

For local development, start with:

```bash
export BASE_URL=http://localhost:8080
export AUTH_HEADER="Authorization: Bearer <jwt_token>"
export TENANT_HEADER="x-tenant-id: public"
# Sandbox only:
# export BASE_URL=https://sandbox.hyperswitch.io
# export FEATURE_HEADER="x-feature: decision-engine"
```

## Request

- Method and path: `GET /analytics/routing-events`
- Parameters:
  - `x-tenant-id` (header, required, string) — see [Environment setup](https://github.com/juspay/decision-engine/blob/main/docs/api-refs/api-ref.mdx#environment-setup).
  - `range` (query, optional, string)
  - `start_ms` (query, optional, integer)
  - `end_ms` (query, optional, integer)
  - `payment_method_type` (query, optional, string)
  - `payment_method` (query, optional, string)
  - `min_transaction_count` (query, optional, integer)
  - `min_score_delta` (query, optional, number)
  - `tolerance_pp` (query, optional, number)
  - `limit` (query, optional, integer)
  - `bucket` (query, optional, string)
- Body: No request body. `tolerance_pp` overrides the auth-band width used to detect `gateway_entered_auth_band` / `gateway_exited_auth_band` events; auth-band events only fire when multi-objective routing is enabled for the merchant.

## Example

```bash
curl "$BASE_URL/analytics/routing-events?range=1d&payment_method_type=CARD" \
  --header "$AUTH_HEADER" \
  --header "$TENANT_HEADER"
```

## Notes

- Analytics reads are ClickHouse-backed and merchant-scoped by the authenticated context.
- `event_type` is one of `leader_changed`, `gateway_entered_auth_band`, `gateway_exited_auth_band`, or `calibration_applied`.
- `calibration_applied` events come from [Autopilot](https://github.com/juspay/decision-engine/blob/main/docs/api-refs/merchant-features.mdx) re-tuning SR hedging/bucket size and carry `bucket_size`/`previous_bucket_size` instead of the score fields.
- `leader_changed` events also say why the lead moved. `leader_change_reason` is `overtaken` when the new leader beat a still-eligible incumbent by at least `min_score_delta`, or `incumbent_stale` when the incumbent stopped being eligible (no score within the staleness horizon, or fewer than `min_transaction_count` transactions) and the best eligible gateway took over without beating it. `score_before` and `previous_score_before` are both gateways' scores in the bucket before the flip, so a falling incumbent can be told apart from an improving challenger.
- `dimensions` summarises each payment method over the whole window and is not capped by `limit`: the current `leader` and when it took over, the leader when the window opened, a `timeline` of who led when (with `gateway: null` for stretches without fresh scores; at most 480 stretches, resampled into equal slots beyond that), `leader_change_count`, the time each gateway led (`leadership`), the time no gateway had a fresh, eligible score (`no_leader_ms`), and every gateway's latest score (`standings`). `leadership` plus `no_leader_ms` adds up to the window, `window_end_ms - window_start_ms`.
- Leaders are tracked per SR v3 cluster: the combination of payment method and the merchant's configured SR dimensions (card network, currency, country, auth type, BIN, UDFs) that scores are kept under. `sr_dimension` on a `leader_changed` event and on each `dimensions` entry names it, with the same value `/decide` reports as the success-rate dimension, for example `ORDER_PAYMENT, DEBIT, CARD, VISA, USD, THREE_DS`. A Visa and a Mastercard cluster of the same payment method therefore have separate leaders and never trade the lead with each other. Each `leader_changed` event also carries the cluster's configured dimensions one by one (`card_network`, `currency`, `country`, `auth_type`, `card_is_in`), the same fields `calibration_applied` events use, so a client can put a leader change and an Autopilot retune of the same cluster side by side. Scores recorded before clusters were have no `sr_dimension` and are tracked per payment method.
- Each `dimensions` entry also carries a `trend` for charting: from where that cluster's traffic starts in the window (or the window start when scores carry over), up to 120 equal slots (`start_ms`, `slot_ms`), with the score updates in each slot (`payments`, one per payment outcome) and each gateway's latest fresh score at each slot's end (`gateways[].scores`, `null` where the gateway had no score within the staleness horizon).
- The newer fields (`leader_change_reason`, `score_before`, `previous_score_before`, `sr_dimension`, `trend`, `window_start_ms`, `window_end_ms`, `dimensions`) are omitted when they have no value, so existing clients are unaffected.
