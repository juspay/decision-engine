title: "Decide"
description: "Route a payment: one ranked connector list, how it was reached, and what each routing layer did."
openapi: "openapi.json POST /decide"
---

`POST /decide` routes a payment: it evaluates the active rule, then ranks the result by success rate, cost and volume commitments.

Authenticate with `Authorization: Bearer <token>` or `x-api-key: <key>`.

### Merchant

The merchant is set by the `x-connected-merchant-id` header, never the body.

| Caller | Without the header | With the header |
| --- | --- | --- |
| Session or API key | Its own merchant | Its own merchant or a [sub-merchant](/sub-merchants), else `403` |
| Service credential | `400` | The merchant named |

### Request ids

`merchant_reference_id` is your own reference and is echoed in the response. `x-request-id` identifies the call; one is generated if absent and returned as a response header.

Required: `payment_id`, `amount`, `currency`, `routing_config.algorithm_for` and `routing_config.eligible_connectors`. Other fields may be omitted or null.

- `amount` is an unsigned integer in minor units.
- Country codes are ISO 3166 alpha-2.
- BINs are strings, so leading zeros are kept.
- A connector needs a nonempty `connector`. `merchant_connector_id` is optional and, when sent, nonempty.
- `metadata` adds custom rule parameters; it cannot override payment fields.
- `payment_type` (`non_mandate`, `setup_mandate`, `ppt_mandate`, …) is matched by rules only.

Unknown fields are rejected.

`connectors` is the order to try: the first is the choice, the rest the retry order. Every connector has the shape `{connector, merchant_connector_id}`.

`outcome` says how the order was reached:

| `type` | Meaning |
| --- | --- |
| `routed` | The configured routing produced the order. |
| `fallback` | Routing could not apply; the eligible connectors, or the unranked rule output, are returned. |
| `no_connector` | Nothing is left to try; `connectors` is empty. Still `200`. |

`strategy` is the layer that set the order (`rule`, `success_rate`, `cost`, `volume_commitment`, `debit_network`, `candidate_order`, `none`); `reason` is the specific case, such as `rule_matched` or `no_active_rule`.

### Codes and messages

| Field | Meaning | Branch on it |
| --- | --- | --- |
| `status` | What a section did, e.g. `cost.status`: `cost_won`, `auth_won` | Yes |
| `reason` | Why, e.g. `outcome.reason`, `volume_steering.blocked[].reason` | Yes |
| `code` | Which problem, on warnings and errors | Yes |
| `message` | Human-readable text | No |

Codes are `snake_case`; new values may be added.

Each routing layer (`rule`, `success_rate`, `cost`, `volume_steering`, `debit_routing`) has a section, null when the layer did not run. `success_rate.diagnostics` is for support and may change.

`warnings` lists problems routed around, such as `rule_input_invalid` with `param` naming the field. Routing problems never fail the call.

## Feedback

Report the outcome with `POST /update-gateway-score`, naming the connector as `"connector:merchant_connector_id"`, or `connector` alone without an account.
