---
title: "Decide"
description: "Evaluate hybrid routing with the unified payment payload."
openapi: "openapi.json POST /decide"
---

`POST /decide` accepts a flat payment payload with nested `card` and `routing_config` objects. It uses the existing hybrid evaluator, including rule selection, Auth Rate routing, A/B experiments, scoring and fallback handling.

Send the same authentication and tenant headers used for `/routing/hybrid` (`Authorization: Bearer <token>` or `x-api-key: <key>`). Merchant sessions and API keys may only name their own `merchant_id`; a cross-merchant request returns `403`. Service callers can use the existing `x-admin-secret` header to act for the named routing scope. `/routing/hybrid` continues to accept its existing request and return its existing response.

## Field mapping

| `/decide` field | Existing internal field |
| --- | --- |
| `amount` | static `amount` and `payment_amount`, plus dynamic payment amount |
| `payment_method_type` | static `payment_method` |
| `payment_method_sub_type` | static `payment_method_type` |
| `card.card_isin` | `card_bin` |
| `card.card_extended_bin` | `extended_card_bin` |
| `card.card_issuer` | `issuer_name` |
| `card.card_issuing_country_code` | `issuer_country` |
| Root `merchant_id` | static `created_by` / dynamic merchant ID |
| `routing_config.eligible_connectors` | hybrid candidate/fallback input |
| `payment_merchant_connector_id` | `gateway_id` / account-qualified dynamic connector |

The required fields are `payment_id`, `merchant_id`, `amount`, `currency`, `routing_config.algorithm_for` and `routing_config.eligible_connectors`. Every input connector requires a nonempty `gateway_name`. `payment_merchant_connector_id` is optional: when sent it must be nonempty, and when omitted or null the connector is named by its gateway alone, as a hybrid `fallback_output` entry without `gateway_id` is (rules then match it only by name, and success-rate scores are keyed by the gateway name). Other fields may be omitted or null. Amounts are unsigned integers in minor units; BINs are strings and preserve leading zeros.

Country codes use ISO alpha-2 values. The adapter translates them to the configured country names for rule matching. Other configured enum values retain an exact match when available, otherwise a case-insensitive match. Existing rule schemas and stored configurations keep their current names.

`merchant_id` is the routing scope formerly called `created_by`; integrations must continue sending the same identifier (the HS profile ID where applicable). `routing_config.algorithm_for` remains explicit and required; it is not inferred from `payment_id`.

`amount` is the single payment amount in this contract. It supplies both existing rule parameters, `amount` and `payment_amount`, without changing stored rule definitions. `metadata` supplies custom rule parameters without overwriting configured or reserved fields. `authentication_type` supplies both rule and dynamic authentication data. Preferred accounts and ranking/elimination options are forwarded to the existing decider; feature and experiment gates still control whether it runs. `country` takes precedence over `billing_country`, then `business_country`.

The removed fields (`payment_type`, `transaction_type`, EMI fields, `internal_metadata`, `order_amount`, `payment_amount`, `udfs`, `payment_metadata`, `payment_source`, `auth_type` and `channel`), old `context` / `created_by`, top-level card fields and `fallback_connectors` are not accepted by `/decide`. Other endpoints retain their existing contracts. Missing required fields, unknown fields and incorrect JSON types return `400` in the standard invalid-request format.

## Response

```json
{
  "evaluated_connectors": [
    { "gateway_name": "worldpay", "payment_merchant_connector_id": "mca_wp" }
  ],
  "decision": {
    "outcome": "routed",
    "source": "SR_SELECTION_V3_ROUTING",
    "decision_id": "req_123"
  },
  "static_routing": {
    "status": "success",
    "output": { "type": "priority", "connectors": [ ... ] },
    "evaluated_output": [ ... ]
  },
  "dynamic_routing": {
    "status": "success",
    "decision": {
      "decided_gateway": "worldpay:mca_wp",
      "fallback_gateways": ["checkout:mca_cko"],
      "routing_approach": "SR_SELECTION_V3_ROUTING",
      "gateway_priority_map": { "worldpay:mca_wp": 0.94, "checkout:mca_cko": 0.91 },
      "multi_objective_info": null,
      "volume_steer_info": null
    },
    "fallback_connectors": null
  }
}
```

`decision_id` matches the `x-request-id` response header. `source` identifies the static algorithm or dynamic routing approach; `eligible_connectors` means hybrid used the supplied candidates after static evaluation failed. `outcome` is `routed` for a selection, `fallback` when hybrid uses a fallback, or `no_active_algorithm` / `no_eligible_connector` for an empty successful result.

The endpoint preserves hybrid's connector order, selection and errors. When there is no active rule, hybrid can still return the supplied candidates as a fallback. Existing hybrid candidate filtering still applies: a rule output outside the supplied candidate list falls back to eligible candidates. If a legacy rule returns only a gateway name, its response account ID is null. A dynamic success returns the same winning connector that hybrid puts in `evaluated_connectors`.

`static_routing` and `dynamic_routing` are the hybrid evaluator's own sections, unchanged, so a `/decide` caller reads the same rule result and SR decision (`fallback_gateways`, `gateway_priority_map`, `multi_objective_info`, `volume_steer_info`) that `/routing/hybrid` returns. Each is present exactly when `/routing/hybrid` would include it: `static_routing` is absent when static evaluation failed, and `dynamic_routing` is absent when SR did not run (the `sr-routing` setting is off or the A/B arm has no SR layer). Analytics record the internal hybrid request and response alongside the original `/decide` request and response, and identify the API route as `decide`. Decisions remain in the hybrid analytics and A/B experiment family.
