---
title: "Decide"
description: "Route a payment: one ranked connector list, how it was reached, and what each routing layer did."
openapi: "openapi.json POST /decide"
---

`POST /decide` accepts a flat payment payload with nested `card` and `routing_config` objects. It runs the rule layer and then success-rate routing, with A/B experiments, cost optimisation, volume commitments, scoring and fallback handling.

Send the same authentication and tenant headers used for `/routing/hybrid` (`Authorization: Bearer <token>` or `x-api-key: <key>`). Merchant sessions and API keys may only name their own `merchant_id`; a cross-merchant request returns `403`. Service callers can use the existing `x-admin-secret` header to act for the named routing scope. `/routing/hybrid` continues to accept its existing request and return its existing response.

The required fields are `payment_id`, `merchant_id`, `amount`, `currency`, `routing_config.algorithm_for` and `routing_config.eligible_connectors`. Every input connector requires a nonempty `gateway_name`. `payment_merchant_connector_id` is optional: when sent it must be nonempty, and when omitted or null the connector is named by its gateway alone, as a hybrid `fallback_output` entry without `gateway_id` is (rules then match it only by name, and success-rate scores are keyed by the gateway name). Other fields may be omitted or null. Amounts are unsigned integers in minor units; BINs are strings and preserve leading zeros.

Country codes use ISO alpha-2 values. The adapter translates them to the configured country names for rule matching. Other configured enum values retain an exact match when available, otherwise a case-insensitive match. Existing rule schemas and stored configurations keep their current names.

`merchant_id` is the routing scope formerly called `created_by`; integrations must continue sending the same identifier (the HS profile ID where applicable). `routing_config.algorithm_for` remains explicit and required; it is not inferred from `payment_id`.

`amount` is the single payment amount in this contract. It supplies both existing rule parameters, `amount` and `payment_amount`, without changing stored rule definitions. `metadata` supplies custom rule parameters without overwriting configured or reserved fields. `authentication_type` supplies both rule and dynamic authentication data. Preferred accounts and ranking/elimination options are forwarded to the existing decider; feature and experiment gates still control whether it runs. `country` takes precedence over `billing_country`, then `business_country`.

`payment_type` is the rule key of the same name (`non_mandate`, `setup_mandate`, `ppt_mandate`, …), which rules use to route mandate payments, for example a processor-token charge to the processor that holds the token. A rule that tests it matches only when it is sent. It does not set the success-rate decider's transaction type.

The removed fields (`transaction_type`, EMI fields, `internal_metadata`, `order_amount`, `payment_amount`, `udfs`, `payment_metadata`, `payment_source`, `auth_type` and `channel`), old `context` / `created_by`, top-level card fields and `fallback_connectors` are not accepted by `/decide`. Other endpoints retain their existing contracts. Missing required fields, unknown fields and incorrect JSON types return `400` in the standard invalid-request format.

`connectors` is the order to try: the first is the choice, the rest the retry order. Every connector in the response, in every section, has the same `{gateway_name, payment_merchant_connector_id}` shape; `payment_merchant_connector_id` is null for a connector named without an account.

`outcome` says how the order was reached:

| `type` | Meaning |
| --- | --- |
| `routed` | The configured routing produced the order. |
| `fallback` | Routing could not apply, so the candidates in request order, or the rule output unranked, answered. |
| `no_connector` | No connector is left to try; `connectors` is empty. The call still returns `200`. |

`strategy` names the layer that set the order (`rule`, `success_rate`, `cost`, `volume_commitment`, `debit_network`, `candidate_order`, `none`) and `reason` the specific case, for example `rule_matched`, `success_rate_ranked`, `cost_optimized`, `no_active_rule`, `rule_output_not_eligible`, `rule_input_invalid` or `success_rate_unavailable`. New values may be added to these enums. `message` is for people reading logs; branch on `reason`.

Each routing layer has a section, null when that layer did not run: `rule` (null when the rule layer failed), `success_rate` (null when the `sr-routing` setting is off or the A/B arm has no SR layer; `status: failed` when the decider failed and the order fell back), `cost`, `volume_steering` and `debit_routing`. `success_rate.diagnostics` carries the decider's internals for support and is not covered by compatibility guarantees.

`warnings` lists problems the decision routed around: `rule_input_invalid` (a request value the routing configuration does not allow; `param` names the request field, such as `card.card_network`, and there is one warning per invalid value), `rule_evaluation_failed` (the rule could not be evaluated for another reason), `rule_output_not_eligible` and `rule_output_partially_eligible` (the rule chose connectors outside `eligible_connectors`), and `success_rate_failed`. Routing problems never fail the call.

`id` is unique per decision. `request_id` matches the `x-request-id` response header.

## Feedback

Report the payment's outcome with `POST /update-gateway-score`, naming the payment by `paymentId` and the connector tried by its decider identifier: `"gateway_name:payment_merchant_connector_id"`, or the bare `gateway_name` for a connector without an account.
